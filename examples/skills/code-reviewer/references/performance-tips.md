# Performance Tips

본 내용은 스킬 정합을 위해 저작됨

SKILL.md `Review Checklist > 3. Performance`의 5개 항목을 리뷰 시 대조할 수 있도록 확장한 문서다.
지적은 **측정 가능한 형태**로 남긴다 — "느릴 것 같다"가 아니라
"요청당 쿼리 N+1건, 목록 100행 기준 101회"처럼 쓴다.

> 최적화 순서: **측정 → 병목 특정 → 수정 → 재측정**.
> 프로파일링 근거 없는 미세 최적화는 `suggestion` 이상으로 올리지 않는다.

## 1. Efficient algorithms (복잡도 분석)

- **확인 방법**: 입력 규모 n이 실제로 커질 수 있는 경로에서 루프 중첩과 자료구조 선택을 본다.
- **위반 신호**
  - 리스트 안에서 `in` 탐색 → 중첩 시 O(n²). 조회 전용이면 집합/해시맵으로 O(n)
  - 루프 안에서 매번 정렬·역순 탐색·문자열 누적 결합
  - 전체 로드 후 메모리에서 필터링(필터를 데이터 소스로 내려야 함)
- **심각도**: 사용자 요청 경로에서 O(n²) 이상이면 **warning**, 무한 증가 입력이면 **critical**

## 2. Database queries optimized

- **N+1 쿼리**: 목록을 조회한 뒤 각 행마다 연관 엔티티를 재조회하는 패턴.
  리뷰에서 가장 자주 나오는 실질 병목이다. 조인 또는 일괄 선로딩으로 1~2회로 접는다.

  ```python
  # 🔴 N+1 — 주문 100건이면 쿼리 101회
  for order in get_orders():
      customer = get_customer(order.customer_id)

  # 🟢 일괄 조회 후 매핑
  orders = get_orders()
  customers = {c.id: c for c in get_customers_by_ids({o.customer_id for o in orders})}
  ```

- **인덱스**: `WHERE` / `JOIN` / `ORDER BY` 컬럼에 인덱스가 있는지, 복합 인덱스의
  선행 컬럼 순서가 쿼리와 맞는지 확인한다. 컬럼에 함수를 씌우면 인덱스가 무력화된다.
- **페이지네이션**: 무한정 커질 수 있는 목록에 `LIMIT`이 없는지 확인한다.
  깊은 오프셋(`OFFSET 100000`)은 커서 기반으로 전환한다.
- **기타**: `SELECT *` 대신 필요한 컬럼만, 반복 쓰기는 배치로, 트랜잭션 범위는 최소로.
- **심각도**: N+1·인덱스 부재·무제한 목록은 **warning**, 대용량 테이블 풀스캔은 **critical**

## 3. Caching implemented where appropriate

- **확인 방법**: 캐시를 넣었다면 세 가지를 반드시 같이 확인한다 —
  **TTL**, **무효화 시점**, **키 설계**.
- **위반 신호**
  - TTL 없는 영구 캐시 → 갱신 누락 시 영구 오염
  - 캐시 키에 테넌트·사용자·권한 스코프가 빠짐 → **데이터 교차 노출(보안 이슈로 승격)**
  - 쓰기 경로에서 무효화 누락 → 읽기가 계속 과거 값 반환
  - 캐시 스탬피드: 동시 만료로 요청이 한꺼번에 원본을 때림
    → 만료 시간 지터, 단일 비행(single-flight) 잠금, 스테일 값 서빙으로 완화
- **심각도**: 스코프 누락 캐시는 **critical**, 무효화 누락은 **warning**

## 4. No memory leaks

- **확인 방법**: "등록했으면 해제했는가", "무한히 자랄 수 있는가" 두 질문으로 본다.
- **위반 신호**
  - 이벤트 리스너·구독·타이머·워처를 등록하고 해제(teardown)하지 않음
  - 상한 없는 캐시·큐·누적 리스트(전역 딕셔너리에 계속 push)
  - 커넥션·파일 핸들을 컨텍스트 매니저 없이 수동 관리하다 예외 경로에서 누수
  - 클로저가 대형 객체를 의도치 않게 오래 붙잡음
- **심각도**: 장기 실행 프로세스에서 무한 증가면 **critical**, 단명 프로세스면 **warning**

## 5. Async operations handled properly

- **확인 방법**: 비동기 컨텍스트 안에서 동기 블로킹 호출이 섞이는지, 예외와 취소가
  전파되는지 확인한다.
- **위반 신호**
  - 이벤트 루프에서 블로킹 I/O·CPU 바운드 작업 직접 실행
    → 스레드/프로세스 풀로 위임
  - 독립 작업을 순차 `await` → 병렬 실행 가능한 구간을 놓침

    ```python
    # 🔴 순차 — 지연 합산
    a = await fetch_a()
    b = await fetch_b()

    # 🟢 병렬 — 지연 최댓값
    a, b = await asyncio.gather(fetch_a(), fetch_b())
    ```

  - 태스크를 생성하고 참조를 버림 → 조기 GC, 예외 유실(fire-and-forget)
  - 동시성 상한·타임아웃·재시도 백오프 부재 → 하위 서비스 과부하
- **심각도**: 이벤트 루프 블로킹·예외 유실은 **warning**, 상한 없는 외부 호출은 **critical**

## 리뷰 종료 전 최종 확인

- [ ] 요청당 쿼리 수를 확인했고 N+1이 없다
- [ ] 커질 수 있는 목록에 페이지네이션과 상한이 있다
- [ ] 캐시에 TTL·무효화·스코프 키가 모두 있다
- [ ] 등록한 리스너·타이머·커넥션에 대응하는 해제 경로가 있다
- [ ] 외부 호출에 타임아웃과 동시성 상한이 있다
